# v0.5.0 优化升级设计方案

> **目标版本**: v0.5.0
> **核心主题**: 配置简单化 × 编辑快速 × 校验准确
> **基于**: v0.4.0（已完成 AI 参数填充、执行验证闭环、执行结果分析）

---

## 设计原则

v0.4.0 打通了"设计→验证→修复"的闭环，但闭环的**起点（配置）依然繁琐、易错、卡顿**。v0.5.0 不增加新的大功能模块，而是**把已有配置链路做深做精**，围绕三个可量化目标：

| 目标 | 现状 | v0.5.0 目标 |
|------|------|------------|
| **配置简单化** | 5+ 处手写 JSON、JSONPath 全靠手敲 | 核心参数零手写 JSON，引用一键选择 |
| **快速** | 每次编辑全量重算，无防抖/增量/缓存 | 非结构化编辑 0 重新布局，校验防抖 |
| **准确性高** | 零静态检查，运行时才暴雷 | 参数引用 / 表达式 / JSON 设计时即校验 |

> 关键洞察：**"参数引用选择器"是同时命中三个目标的支点**——用选代替敲，既简单（不用记 JSONPath）、又准确（不可能引用到不存在的目标）、配合增量更新还快。

## P5.1：可视化参数映射（简单化 + 准确）

> **目标**：消灭 inputParameters 的手写 JSON，把"敲 JSONPath"变成"选引用"。

### P5.1.1：参数引用上下文计算（核心基础设施）

新增工具 `src/utils/referenceContext.ts`，给定当前任务，计算所有**合法可引用源**：

```typescript
export interface ReferenceOption {
  expr: string;          // 如 "${fetch_order.output.orderId}"
  source: 'workflow_input' | 'task_output' | 'workflow_variable' | 'system';
  label: string;         // 展示名
  taskRef?: string;      // 来源任务（task_output 时）
  description?: string;
}

/**
 * 计算当前任务在 DAG 中所有「上游可引用」的数据源。
 * - workflow.input.*  ← workflowDef.inputParameters（v0.4.0 已结构化）
 * - <upstreamRef>.output.*  ← 当前任务的所有祖先任务（拓扑序在前）
 * - workflow.variables.*  ← 当前任务之前的 SET_VARIABLE 任务
 * - workflow.workflowId / correlationId / status 等系统变量
 */
export function getAvailableReferences(
  workflowDef: WorkflowDef,
  currentTaskRef: string
): ReferenceOption[];

/** 反向校验：判断一个 ${...} 表达式引用的根是否在合法集合内 */
export function isReferenceResolvable(
  expr: string,
  available: ReferenceOption[]
): { ok: boolean; reason?: 'unknown_task' | 'forward_ref' | 'malformed' | 'undeclared_input' };
```

**关键点**：祖先计算复用已解析的 `edges`（或对 task 树做一次 ancestor 遍历），保证"不能引用下游/自身任务"。**此工具同时是 P5.1 的选择器数据源与 P5.4 的校验数据源**，一处实现两处复用。

### P5.1.2：结构化键值编辑器（KeyValueEditor）

新增 `src/components/inputs/KeyValueEditor.tsx`，替换原始 JSON textarea，用于 `inputParameters`、HTTP headers、KAFKA headers 等键值结构：

```
┌─────────────────────────────────────────────────────────┐
│ KEY              VALUE                      TYPE          │
│ ┌────────────┐  ┌──────────────────┐ 🔗  ┌────────┐ ✕  │
│ │ orderId    │  │ ${order.output.id}│     │ string │     │
│ └────────────┘  └──────────────────┘     └────────┘     │
│ ┌────────────┐  ┌──────────────────┐ 🔗  ┌────────┐ ✕  │
│ │ amount     │  │ 99.9             │     │ number │     │
│ └────────────┘  └──────────────────┘     └────────┘     │
│ [+ 添加字段]                          [⚙ 高级 JSON 模式] │
└─────────────────────────────────────────────────────────┘
```

- 每行 value 右侧 **🔗 插入引用** 按钮 → 弹出按来源分组的引用选择器（数据来自 P5.1.1）
- value 输入框对 `${...}` 片段做语法高亮 + 失效引用红色下划线
- **「高级 JSON 模式」** 切换开关：高级用户仍可直接编辑原始 JSON（含实时格式校验），双向同步
- 类型选择驱动 value 的输入控件（number→数字框、boolean→开关、object/array→嵌套 JSON）

**涉及文件**：
- `src/components/inputs/KeyValueEditor.tsx`（新建）+ `.css`
- `src/components/inputs/ReferencePicker.tsx`（新建）——引用选择浮层
- `src/components/TaskDetailPanel.tsx` —— inputParameters / HTTP headers 区域改用 KeyValueEditor

### P5.1.3：HTTP / 常用任务的表单化深化

- HTTP body 当为对象时用 KeyValueEditor；为原始文本时保留代码框，顶部加"对象/文本"切换
- URI 输入框接入引用选择器（修复当前"HTTP 字段无 AI/引用辅助"的盲区）

## P5.2：配置一致性与统一存储（简单化）

> **目标**：消除"双重身份"与割裂感，让同一类配置在所有任务类型中长得一样。

### P5.2.1：统一 inputParameters 存储

- 现状：HTTP 参数同时存在 `task.httpRequest` 与 `task.inputParameters.http_request`，由 `handleHttpChange` 双写维护（易不同步）
- 方案：**载入时归一化**——`conductorParser` 解析时将 `httpRequest` 合并进 `inputParameters.http_request` 作为单一内部真相源；`conductorGenerator` 导出时仍产出 Conductor OSS 标准结构（向后兼容旧 JSON）
- 删除 `TaskDetailPanel` 中的双写分支，`handleHttpChange` 简化为单一路径

### P5.2.2：上下文帮助系统

- 新增 `src/config/taskFieldHelp.ts`：集中维护各任务类型字段的帮助文案与示例值（替代当前散落在 JSX 里的零散说明）
- 字段标签旁统一加 `ⓘ` Tooltip，hover 显示用途 + 示例 + Conductor 文档链接
- KeyValueEditor 空状态显示该任务类型的"推荐参数"占位提示

### P5.2.3：快捷片段重构

- 片段库扩充并按场景分组（输入引用 / 输出引用 / 变量 / 条件表达式 / JQ 范例）
- 片段入口从 inputParameters 专属，下沉为所有代码/表达式字段通用（INLINE expression、DO_WHILE condition 等）

## P5.3：编辑性能优化（快速）

> **目标**：把"每次编辑全量重算"改为"按需最小重算"。

### P5.3.1：结构化 vs 非结构化更新分流

`workflowStore.updateTask` 增加更新分类（按字段名自动判定，或显式传入 `structural` 标志）：

| 类别 | 字段示例 | 处理 |
|------|---------|------|
| **非结构化** | inputParameters、description、retryCount、timeoutSeconds、httpRequest、expression、name(label) | 跳过 `parseWorkflow` + `getLayoutedElements`；仅原地更新对应 `node.data.task` + `taskMap`，**保留现有坐标** |
| **结构化** | 增删任务、增删分支、改 type、改 decisionCases 键名 | 走原有全量重算路径 |

预期：编辑参数值的场景 **重新布局调用降为 0**，大流程编辑从卡顿变流畅。

### P5.3.2：校验防抖

- `validateWorkflow` 在连续输入时以 ~300ms 防抖执行（`src/utils/debounce.ts` 或复用 hook）
- 校验结果就绪后再更新 `validationResults`，避免逐字符触发全量递归校验

### P5.3.3：布局缓存与小流程短路

- 计算 workflow 的"结构签名"（节点引用名 + 边集合 hash）；签名不变时 `getLayoutedElements` 直接复用上次坐标
- <30 节点的流程跳过蛇形布局分支，走轻量直排，降低首屏与切换开销

## P5.4：静态校验增强（准确）

> **目标**：把"运行时才暴雷"的错误提前到"设计时就提示"。

### P5.4.1：参数引用静态校验

新增校验规则 `validateParameterReferences(workflowDef)`，深度遍历每个任务 inputParameters 中的 `${...}`：

| 场景 | 级别 | 提示 |
|------|------|------|
| `${taskX.output.f}` 中 taskX 不存在 | ❌ error | 引用的任务不存在 |
| `${taskX.output.f}` 中 taskX 是当前/下游任务 | ❌ error | 不能引用后续任务的输出 |
| `${workflow.input.f}` 中 f 未在 inputParameters 声明 | ⚠️ warning | 工作流入参未声明此字段 |
| `${workflow.variables.v}` 无对应 SET_VARIABLE | ⚠️ warning | 变量可能未被设置 |
| 畸形 `${...}`（双点、空路径等） | ⚠️ warning | 表达式格式可疑 |

复用 P5.1.1 的 `getAvailableReferences` / `isReferenceResolvable`，**与选择器同源**，保证"能选的一定合法、合法的一定能选"。

### P5.4.2：表达式轻量预检

- INLINE/LAMBDA `expression`、DO_WHILE `loopCondition`、DECISION `caseExpression`：做**低成本**静态检查（括号/引号配平、非空、明显非法字符），不做完整 JS 解析以保证性能
- JSON_JQ_TRANSFORM `queryExpression`：基础非空与首字符合法性检查

### P5.4.3：字段级实时反馈

- `TaskDetailPanel` 从 `validationResults` 中过滤出"当前任务 + 当前字段"的条目，在对应输入控件旁渲染 ❌/⚠️ 图标 + 悬浮原因
- JSON / KeyValueEditor 的解析错误**不再静默吞掉**：实时显示红色行内错误，保留上一次有效值不丢失
- 与 v0.4.0 的"去修复"跳转打通：`switchToEditAndFocusParam` 落点高亮对应字段

## 验收标准

### 配置简单化
- [ ] 配置一个 HTTP 任务的 inputParameters / headers **全程无需手写 JSON**
- [ ] 引用上游任务输出时通过下拉选择完成，无需记忆 JSONPath 语法
- [ ] 同一类键值配置在 HTTP / SIMPLE / KAFKA 等任务中交互一致

### 快速
- [ ] 编辑参数值（非结构化）时，重新布局调用次数为 **0**，节点坐标不跳动
- [ ] 连续输入时校验以防抖执行，不再逐字符全量递归
- [ ] 100+ 节点工作流编辑无可感知卡顿

### 准确性高
- [ ] 引用不存在 / 下游任务时，设计时即报 ❌ error（不再等运行时）
- [ ] 工作流入参未声明的引用给出 ⚠️ warning
- [ ] JSON 格式错误实时行内提示，不再静默吞掉
- [ ] 选择器可选的引用 100% 通过校验（选择器与校验同源一致）
