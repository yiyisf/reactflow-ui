# AI 工作流编排组件 — 未来设计规划

> **版本**：v1.0  
> **状态**：已批准，待实施  
> **适用分支**：`feat/ai-workflow-ide`

---

## 一、定位重塑：从"画布 + AI 助手"到"AI 原生编排工作台"

当前形态的本质是 **"画布为主体、AI 是挂在旁边的聊天框"**。未来形态应反转为：

> **AI 是编排的主要执行者，人是意图的表达者和决策的把关者，画布是双方共享的"白板"。**

这意味着三个根本转变：

| 维度 | 现在 | 未来 |
|---|---|---|
| 交互主体 | 用户操作画布，AI 辅助 | 用户表达意图，AI 编排，画布呈现共识 |
| AI 角色 | 单轮问答 + 生成 JSON | 有规划、能自查、可多步执行的 Agent |
| 用户门槛 | 需理解 Conductor 任务模型 | 业务语言进、业务语言出，技术细节按需下钻 |

---

## 二、用户分层：四类角色，一套组件

提升覆盖用户范围的关键不是把界面做简单，而是**让同一个工作流对不同角色呈现不同的抽象层**：

| 角色 | 特征 | 期望体验 |
|---|---|---|
| **业务人员** | 不懂编排 | 用自然语言描述流程，看"业务步骤卡片流"，不接触 ref/type/inputParameters |
| **流程设计师** | 懂流程、不懂代码 | 标准视图操作分支/并行/审批，参数通过表单而非 JSON 配置 |
| **编排开发者** | 全技术栈 | 开发者视图：全量节点、JSON、表达式、Schema 校验，AI 是结对编程伙伴 |
| **运维/值班** | 关注执行 | 运行视图：失败诊断、影响面分析、修复操作，AI 是 SRE 副驾驶 |

现有 `business / standard / developer` 三层视图是正确的起点，但未来要做到 **"AI 的语言也分层"**——同一个变更提案，对业务人员说"在支付后增加了人工确认环节"，对开发者展示 patch ops 和 JSON diff。

---

## 三、核心架构：四层能力栈

```
┌─────────────────────────────────────────────────────────┐
│  L4 体验层   分层视图 · 对话 · 提案审阅 · 运行洞察           │
├─────────────────────────────────────────────────────────┤
│  L3 智能层   Agent 引擎 · 规划器 · 自验证 · 修复器           │
├─────────────────────────────────────────────────────────┤
│  L2 知识层   工作流库 RAG · 企业规范 · Schema 注册           │
├─────────────────────────────────────────────────────────┤
│  L1 内核层   Headless 编排内核 · 工具协议 · 事件总线          │
└─────────────────────────────────────────────────────────┘
```

### L1 内核层：Headless 优先

这是扩展能力的根基，把"编排能力"从 UI 中剥离成无头内核。

**`@workflow/core`**：纯函数的 WorkflowDef 操作引擎（patch、diff、validate、layout），不依赖 React，可在 Node.js、测试环境、CI 流水线中独立运行。

**工具协议（Tool Registry）**：内置工具（replace/patch/query/validate/search）与集成方自定义工具走同一注册机制。集成方可注册领域工具，AI 自动获得这些能力：

```typescript
orchestrator.registerTool({
    name: 'deploy_workflow',
    description: '将工作流部署到指定环境',
    parameters: { /* ... */ },
    execute: async (args) => { /* 集成方实现 */ },
});
// AI 现在可以主动调用 deploy_workflow
```

**事件总线**：全生命周期事件对外暴露，集成方可做埋点、审计、联动：

```typescript
// proposal:created | proposal:accepted | proposal:rejected
// execution:failed | ai:tool_called | ai:plan:step
orchestrator.on('proposal:accepted', ({ def, diff, user }) => audit.log(...));
```

**模型适配抽象**：OpenAI/Anthropic 之外，支持集成方注入自有 LLM 网关（企业内通常有统一代理），适配层只约定 `streamChat` 的事件协议。

### L2 知识层：让 AI "懂这家公司"

AI 编排专业性的上限取决于上下文质量，而非模型本身。

**工作流库 RAG 化**

现在是把库列表塞进 system prompt（线性膨胀、不可扩展）。未来库元数据应向量化/索引化，AI 通过检索工具按需拉取，支持千级规模的子流程库，且检索精度随业务语义而非精确名称匹配。

**Schema 注册表**

任务的输入输出 Schema（HTTP 接口契约、子流程参数）注册后，AI 生成的参数映射可被静态校验——"生成即可验"而非"生成后人查"。

```typescript
schemaRegistry.register('send_notification', {
    input: { userId: 'string', message: 'string', channel: 'email|sms' },
    output: { messageId: 'string', status: 'sent|failed' },
});
```

**企业规范注入**

超时标准、重试策略、命名规范、必备审批环节等，以结构化规则（而非散文 prompt）注入，AI 生成时遵守，校验器兜底：

```typescript
orchestrator.setRules([
    { id: 'timeout-required', level: 'error',
      message: 'HTTP 任务必须设置 timeoutSeconds',
      check: (task) => task.type !== 'HTTP' || !!task.timeoutSeconds },
    { id: 'approval-before-payment', level: 'warning',
      message: '支付操作前建议有人工审批环节',
      check: (def) => /* ... */ },
]);
```

**历史经验沉淀**

用户对提案的接受/拒绝/修改记录回流为偏好信号，逐步个性化（"这个团队总把超时改成 300s"），降低高频修改的 AI 建议与用户预期间的摩擦。

### L3 智能层：从"单轮生成"到"Agent 编排"

这是专业性提升的核心，分四个能力模块。

#### ① 规划器（Planner）

复杂需求先出计划再动手，用户确认计划后 AI 逐步执行：

```
用户："把订单流程改造成支持多仓库发货，失败要能回滚"

AI 计划卡片：
  ① 查询当前流程结构与库中可复用的仓库分配子流程        [待执行]
  ② 将"发货"节点重构为 FORK_JOIN 多仓库并行执行        [待执行]
  ③ 为每个仓库操作增加配对回滚任务（SAGA 补偿链路）      [待执行]
  ④ 校验整体结构并生成变更提案                          [待执行]

  [开始执行]   [调整计划]
```

计划本身就是一种轻量提案——让用户在动手前纠偏，这对非技术用户尤其重要。

#### ② 多轮工具循环（Agentic Loop）

AI 调用 `get_workflow_state` 后结果回流给模型继续推理，直到任务完成。这是当前架构最大的缺失，是一切高级能力的前提。配套设计：

- Message 模型支持 `tool_calls` / `tool_result` 角色；
- 自动上下文压缩（避免长对话超限）；
- 步数上限 + 循环检测（防止无限递归）；
- 每步实时进度展示，用户可随时 Stop。

#### ③ 自验证闭环（Self-Healing Generation）

AI 生成提案后自动调用校验器，发现错误自行修复后再呈现给用户。用户看到的提案永远是"校验通过"的。

校验能力升级：
- **语法校验**：taskReferenceName 唯一性、类型合法性（现有）；
- **数据流校验**：`${task_ref.output.xxx}` 引用的上游是否存在且有该输出；
- **规范校验**：L2 注入的企业规则；
- **可达性分析**：SWITCH 分支死路检测，孤立节点检测；
- **循环检测**：DO_WHILE 缺少终止条件检测。

#### ④ 运行态修复器（Runtime Copilot）

运行视图下 AI 的目标函数从"编排"切换为"诊断与恢复"：

- **失败自动 RCA**：拉取失败任务的输入/输出/错误日志，定位数据问题/配置问题/依赖故障；
- **分级修复方案**：「重试该任务」「跳过并继续」「修改定义后从断点重跑」，每个方案标注影响范围；
- 修复操作同样走提案-确认流，高危操作可配置要求二人确认；
- 支持对接 `ExecutionActions` 中的 `onRerunFromTask` / `onSkipTask` 执行修复。

### L4 体验层：五个关键设计

#### ① 提案体验 2.0 — Ghost Preview + 分粒度接受

当前：整包替换 + 文字 diff 描述。未来：

- **画布幽灵预览**：新增节点以半透明"幽灵态"渲染，删除节点显示红色删除线，修改节点支持新旧双态对比切换；
- **变更卡片可逐条接受/拒绝**：一个提案拆成原子变更列表，用户可勾选部分采纳；
- **基线保护**：提案携带创建时的画布快照；若用户在审阅期间手动改了画布，提案自动标记"已过期"，提供"基于最新画布重新生成"，杜绝静默覆盖；
- **完整 undo 链**：接受提案后可一键回滚。

#### ② 多模态输入 — 降低表达门槛

业务人员表达流程的方式从来不是文字描述：

- **截图/手绘流程图 → 工作流**：拍白板照片，AI 识别节点和连线生成草稿；
- **文档/SOP → 工作流**：粘贴操作手册或 Excel 步骤清单，AI 抽取成流程；
- **录音口述**（可选）：会议中口述的流程变更直接转为提案。

#### ③ 双向画布交互 — 画布即提示词

- 圈选若干节点 → "把这几步改成并行"；
- 拖边到空白处 → AI 建议此处可插入的节点类型；
- 节点错误图标 → 点击即"让 AI 修复此问题"；
- 多选节点 → 右键"AI 重构选中片段"。

当前的 selected-node context strip 是正确的雏形，未来扩展到多选、框选、边选。

#### ④ 解释与教学模式

专业性的另一面是帮用户理解工作流：

- 任意节点/分支可问"这是什么、为什么这样设计"；
- AI 修改后主动解释理由（"我加了超时是因为企业规范要求 HTTP 任务必须设置 timeoutSeconds"）；
- 业务人员逐步看懂标准视图，形成自然的能力爬梯，无需专项培训。

#### ⑤ 信任与可控性基建

AI 能力越强，信任机制越重要：

| 控制点 | 设计 |
|---|---|
| 操作分级 | 读 < 改定义 < 运行态干预，按角色配置 AI 权限上限 |
| 全量审计 | AI 行为日志（谁/何时/做了什么/采纳与否）对接企业审计系统 |
| 永不直接落画布 | 所有 AI 写操作强制走提案流 |
| 高危二次确认 | 运行态修复操作可配置"需要第二人确认" |
| 完整 undo | 接受提案后保留回滚入口 |

## 四、组件交付形态：三种集成深度

```
全量组件（开箱即用）
  <AiOrchestrator config={aiConfig} workflowLibrary={lib} executionActions={ops} />

可组装件（自由布局）
  <Canvas />  <AiPanel />  <ReviewLayer />  <RuntimePanel />  独立导出

Headless SDK（无 UI，纯能力）
  const orchestrator = createOrchestrator(config);
  const proposal = await orchestrator.propose("把审批流改成并行");
  // 集成方自渲染，或嵌入 VS Code 插件、小程序、后端流水线
```

**扩展点清单**：
- 自定义节点类型与渲染器
- 自定义工具注册（Tool Registry）
- 自定义校验规则（Rule Engine）
- 自定义提示词域（systemPromptExtra / systemPrompt 覆盖）
- LLM 网关适配器（企业内部代理）
- 生命周期事件钩子（事件总线）
- 国际化（i18n）

## 五、演进路线（三阶段）

### Stage 1 — Agent 化地基（最高优先级）

**目标**：AI 能"查→想→改→验→报"自主走完一个复杂编排任务。

- Message 模型重构（支持 `tool_calls` / `tool_result` 角色）
- 多轮工具循环（Agentic Loop，含步数上限与自动终止）
- 提案基线保护（快照 + 过期检测）
- Ghost Preview（幽灵态画布预览）
- 自验证闭环（生成后自动修复校验错误）
- 计划卡片 UI（Planner 第一版）

### Stage 2 — 知识与体验跃迁

**目标**：千级流程库下 AI 仍准确复用；运行失败可一键获得可执行修复方案。

- Tool Registry 开放（集成方自定义工具）
- 工作流库 RAG 化（向量检索替代 prompt 列表）
- Schema 注册表与数据流校验
- 分粒度提案接受（逐条接受/拒绝）
- 运行态 RCA + 修复提案（Runtime Copilot）
- 规范注入（企业规则引擎 v1）

### Stage 3 — 全角色覆盖与生态

**目标**：业务人员无培训可独立完成"描述→审阅→上线"全流程。

- 多模态输入（截图/文档 → 工作流）
- 分层 AI 语言（同一提案对不同角色使用不同描述）
- 双向画布交互（框选、多选、拖边 → AI 建议）
- 解释与教学模式
- Headless SDK 与可组装件独立导出
- 审计日志 + 操作权限分级
- 历史偏好学习

## 六、北极星指标

| 指标 | 含义 | 目标方向 |
|---|---|---|
| **提案采纳率** | AI 提案被接受（含部分接受）的比例 | 衡量生成质量 |
| **零修改采纳率** | 提案不经人工修改直接采纳的比例 | 衡量专业性 |
| **非技术用户完成率** | 业务角色独立完成流程创建的比例 | 衡量覆盖度 |
| **MTTR 缩减** | 运行失败从发现到修复的时长 | 衡量运行态价值 |
| **意图轮次** | 完成一个编排目标所需的对话轮数 | 衡量交互效率 |

## 七、与当前实现的收敛点

Stage 1 精准对应当前审计中识别的三个架构级缺陷：

| 当前缺陷 | Stage 1 解决方案 |
|---|---|
| 无工具回流（单轮管道） | 多轮 Agentic Loop + Message 模型重构 |
| 提案覆盖手动编辑 | 基线保护 + 过期检测 |
| 新增节点提案期不可见 | Ghost Preview 幽灵态渲染 |

三个缺陷都是"提案体验 2.0"和"Agent 化地基"的子集，新旧规划在此完全收敛，Stage 1 即可同时解决遗留问题。
