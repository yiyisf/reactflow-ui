自助接入
新团队不靠陪跑，自己把第一个流程跑起来

@yiyi_zhang/reactflow-ui 是供内部项目嵌入的工作流 IDE SDK。v1.3.0 让一个从未接触过平台的团队，在测试环境里自己完成：登记产品 → 规范命名建流程 → 接上已有接口 → 试跑 → 申请上线。

  • ＋扩展点注册 WorkflowIdeProvider
  • ＋自助接入向导与命名生成器
  • ＋申请上线与进度
  • ＋接口导入（OpenAPI / Swagger / Postman / curl）
  • ＋接入埋点 TelemetrySink
$ npm install @yiyi_zhang/reactflow-ui@1.3.0 reactflow react react-dom
先在页面里走一遍 在工作台里亲手试 宿主接入指南

v1.3.0 已于 2026-10-24 发布，详见 CHANGELOG。演示站运行在模拟治理服务上，没有接真实后端；不接这些扩展点时，SDK 行为与 1.2.0 完全一致。

        5.申请上线 示意
        
              
        只有 tmp 类型的临时流程可以申请上线：选择目标类型，预览正式名称（类型段被替换），提交后在 IDE 里看审批进度。真实 SDK 用指数退避轮询（2 秒起，30 秒封顶），到 APPROVED / REJECTED / SYNCED 停止；这里每点一次“刷新进度”相当于一次轮询。

          API IMPORT
          
        
          接口导入：已有接口，几步变成流程步骤
          
        
          工具栏“导入接口”：粘贴或上传 → 自动识别格式 → 勾选接口 → 插入。每个接口生成一个 HTTP 业务动作，编译为 Conductor HTTP 任务（http_request.uri / method / headers / body）。
          
      
          

      
          
        
          
          四种来源
          
          粘贴就能认出格式
          
          
          
            
          
              
          格式1.3.0说明
          
              
                
          OpenAPI 3.x（JSON）支持选择一个或多个 operation；servers[0].url、本地 $ref、security 推断认证头
          
                
          Swagger 2.0（JSON）支持schemes / host / basePath、definitions 引用
          
                
          Postman Collection v2.1（JSON）支持文件夹作为标签；{{var}} 转为 ${workflow.input.var}
          
                
          curl 命令支持方法、URL、头、-d / --data-raw 请求体、-u、行尾 \ 续行
          
                
          YAML 格式的 OpenAPI不支持暂不支持：请先转为 JSON 再导入（不引入 YAML 依赖）
          
                        
            
          
          
          
        
          
        
          
          敏感头不落定义
          
          凭据永远不写进流程
          
          
            
            
          • Authorization / Cookie / X-Api-Key、名称含 token、secret、api-key 的头，以及 curl -u，一律换成 ${workflow.input.xxx} 占位
            • 
            
          • 导入面板提示改用凭据管理；步骤引用的 workflow.input.* 自动补进流程入参
            • 
            
          • 出参取 2xx 响应 schema，键为 response.body.<字段>
            •

          EXTENSION POINTS
          
        
          统一扩展点：配置一次，处处生效
          
        
          此前每加一个能力就要在两个 IDE 上各传一遍 props。现在用 WorkflowIdeProvider 在外层配置 providers，页面里所有 IDE 实例共用；每个功能自己检查对应 provider 在不在，不在就不显示入口。

          OnboardingProvider 对接治理服务
          
          契约与治理服务接口一一对应
          
          
          
            
          
              
          方法治理服务接口说明
          
              
                
          listDomainsGET /api/library/domains业务域全局列表
          
                
          listMyProductsGET /api/products/mine我的产品（名称、业务域、状态、角色）
          
                
          startTrialPOST /api/onboarding/trial登记产品并开通试用；已被他人占用返回 conflict 与负责人
          
                
          requestPromotionPOST /api/onboarding/promote提交上线申请，返回 requestId
          
                
          getPromotionGET /api/onboarding/promote/{id}SUBMITTED → REVIEWING → APPROVED / REJECTED → SYNCED
          
                
          getContext由宿主从会话 / 配置取得env、当前用户、trialEnabled（生产为 false）
          
                        
            
          
          
          
        
          
        
          
          升级无感
          
          不接就不变
          
          
            
            
          • 只传 libraryProvider、不用 WorkflowIdeProvider 的现有写法，行为与 1.2.0 一致
            • 
            
          • 没有 onboarding 就没有“新建流程”“申请上线”“开始试用”
            • 
            
          • 按字段比较引用：每次渲染新建 providers 对象没关系，但 provider 实例要只创建一次，否则目录会反复重载
            • 
          
          
        
          
      
          
    
          

    
    
          
      
          
        
          TELEMETRY
          
        
          埋点：看得见的推广漏斗
          
        
          推广进度不再靠手工统计。TelemetrySink.track(events) 由 SDK 按“5 秒或 20 条”攒批、页面隐藏时 flush，宿主把事件送到自己的事件接口即可；没有 sink 时事件直接丢弃。

            3. 
        
          3. 首次试跑sandbox_run
            4. 
        
          4. 上线promotion_requested · promotion_state

          首批事件（设计 §5.2）
          
          事件与用途
          
          
          
            
          
              
          事件触发用途
          
              
                
          ide_openedIDE 挂载活跃度
          
                
          trial_started向导完成产品登记漏斗：开始试用
          
                
          workflow_created向导生成骨架漏斗：首份草稿
          
                
          step_added插入步骤（props.source：builtin / library / import / template）能力复用情况
          
                
          api_imported接口导入（props.count、props.format）接口导入使用率
          
                
          sandbox_run本地沙箱试跑（props.result）漏斗：首次试跑
          
                
          workflow_saved触发 onSave保存
          
                
          promotion_requested / promotion_state申请上线 / 状态变化漏斗：上线
          
                
          ai_event透传现有 onAiEvent 的类型（不含内容）AI 使用情况
          
                        
            
          
          
          
        
          
        
          
          不采集
          
          只记“用了什么”
          
          
          事件只有名称、时间、IDE 类型、流程名与简单属性（props 里非 string / number / boolean 的值会被剔除）。
          
          
            
            
          • 参数值
          • 表达式
          • 提示词
          • 对话内容
          • 执行数据
            • 
          
          
          
          生产首跑（KPI 口径）由服务端按执行数据判定，SDK 不上报“首跑成功”。

          TRY IT
          
        
          在工作台里亲手走一遍
          
        
          工作台跑在模拟治理服务上，所有数据都是合成的演示数据。下面的按钮名称取自当前演示站，界面调整时以工作台为准。
          
      
          
      
          
        
          
          
            
            
          1. 打开 /app 工作台。顶栏 演示设置 里的 环境 默认是 TEST（开放自助试用）；切到 PROD 可以看到降级：没有“开始试用”，新建流程的类型可选 custom / std。
            2. 
            
          2. 在 演示设置 里点 重置产品（在 TEST 下）：画布清空，出现 开始试用 引导卡片。登记产品时试试 cmdb，会得到“已被他人占用”及负责人列表。
